# Фронтенд по контекстам, без правил Календаря

Экраны разложены по тем же контекстам, что и бэкенд: Планирование, Идентификация, Администрирование. Каркас —
маршруты, сессия, шапка — в `app/`. Общий клиент API и тексты ошибок — в `shared/`. Папки `pages/` нет: страница —
корневой компонент своего контекста. Тесты лежат рядом со своими файлами.

Feature-Sliced Design не берём. Слои pages/widgets/features/entities для трёх контекстов лишние, а слой entities
тянет завести на клиенте свою модель Календаря. Плоский список страниц прячет границу: правило бронирования легко
дописать рядом с экраном.

Правила Календаря на клиент не переезжают (ADR-0006). Горизонт планирования, Лимит бронирований и занятость Слота
приходят с сервера. `scheduling/model` только показывает присланное: группирует Слоты по дням, рисует сетку месяца
и подписывает время. Число дней Горизонта сервер уже прислал. Модель раскладывает его по гражданским дням Гостя,
включая дни без Слотов, чтобы сетка показала ноль. Это подпись календаря, а не решение, можно ли забронировать
Слот: его принимает сервер. Экран показывает статус, который сервер уже выставил, и текст ошибки из ответа. Форма
настроек по-прежнему проверяет введённые числа до отправки, чтобы показать ту же ошибку поля; к решению о Слоте
это отношения не имеет.

Клиент один: `shared/api.ts`. Вызов бронирования в `scheduling/api` идёт через него.

Контексты не импортируют друг друга. Страница читает сессию из `app/session` и не импортирует маршруты: маршруты
сами собирают страницы, обратная связь замкнула бы цикл. `shared/` экраны не импортирует.
